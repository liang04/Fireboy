# 关卡 7 / 8 设计说明（组合创新增量）

> 决策背景：仓库里 1–6 关的机关库已完成「串联 → 并联 → 永久 vs 临时 → 电源资源化 → 总复习」
> 的进阶曲线。本轮在**不改任何引擎/机关代码**的前提下，用已有 8 类机关拼出两个
> 此前从未出现过的玩法结构，并由生成器 + 求解器 + 冒烟测试三层把关。

---

## 0. Fun Hypothesis（本轮增量）

1–6 关验证了「我做完你接着做 / 各做各的互相开门 / 人 vs 箱子投资性质」。
剩下两件没碰过的张力：

| 缺口 | 之前的状态 | 本轮补上 |
|---|---|---|
| **远距离间接协作** | 两人永远在同一片场地，开关和受益者在同屏就近 | 第 7 关：一道谁也无法逾越的毒液护城河把两人**物理隔离**，只能靠机关远程互相供电 |
| **一个触发器带多个异种受控物** | 每个 channel 只接 1 扇门 / 1 台平台 | 第 8 关：一根「总闸」拉杆同时控制 1 扇门 + 2 台纵向电梯（三者完全不同种类） |

第二条正是 channel 解耦架构**最初就想证明的事**——受控物不需要知道谁在控制它。

## 1. 关卡 7「遥供双塔」

### purpose
把「移动平台 = 电源资源」从第 5 关的**就近协作**升级为**遥供协作**：你踩的板在你看不见的
对岸，对方电梯通不通电，取决于你有没有一直站在那里。

### player experience goal
玩家第一次强烈感知「我被对方的节奏控制」：火娃中途松开板，水娃的电梯会停在半空等——
不致死，但立刻教会什么叫「你按一下，我才能动一下」。

### 结构（60×22）

```
左塔(火)        毒液护城河 8 格宽     右塔(水)
F ──踩板EB──[电梯EA]     ~~~~~~~~~~~~~~~~     [电梯EB]──拉杆EA── Q
E(左塔顶)                                            W
```

机关链（求解器给出的最优解与设计意图完全一致）：

| 步骤 | 谁 | 做什么 | 效果 |
|---|---|---|---|
| 1 | 火娃 | 踩住压力板 EB（火区地面，板 channel=EB） | 右塔（水娃）电梯通电 |
| 2 | 水娃 | 乘电梯升上右塔顶 | — |
| 3 | 水娃 | 拉下自锁拉杆 EA（channel=EA） | 左塔（火娃）电梯通电 |
| 4 | 火娃 | 这才敢松开板 EB → 乘自己的电梯上左塔顶 | 各进各门 |

### 关键设计决策（每条都有 rationale）

| 决策 | rationale |
|---|---|
| 护城河用 **8 格宽毒液**（对两人都致命、远超 5 格跳远上限） | 物理隔离必须绝对可靠——如果可跳过，火娃就能肉身过河自己去拉杆，整条遥供链崩塌 |
| 板 EB 放**火区地面**而非高台 | 第 5 关的高台是为了防木箱代踩；本关无箱、且对岸角色绝对到不了，平地即可，少一层学习成本 |
| 杠杆 EA 是**自锁**且放在水门之前 | 水娃到顶后必须先拉杆才能走到 Q——拉杆从「可选项」变成「必经之路」，杜绝水娃丢下火娃直接进门 |
| 火娃松开板 → 水娃电梯停半空 | **软同步**而非硬惩罚：电梯停在半空，水娃安全但无法前进，火娃回去踩板即恢复。用「卡住 3 秒」教学比用「死亡」教学温和 |

### inputs / outputs / edge cases / failure states

- inputs：火娃站板（持续）、水娃乘梯（等平台降到 from）、水娃在塔顶按交互拉杆
- outputs：EB 平台受电运行、EA 平台受电运行、Q/E 门各自可进
- edge case：火娃在错误时机松板 → 水娃被悬空（可逆，无死亡）
- failure state：若板 EB 被误放到水娃区，则火娃永远够不着 → 无解（校验器已能抓出）

## 2. 关卡 8「总闸·同台」

### purpose
系列收官的情感高点。全游戏第一次**一个触发器管三个异种受控物**：
`总闸拉杆 M → 门 M（打开）+ 火娃电梯 + 水娃电梯（同时启动）`。

### player experience goal
热场只做一件旧事（推箱开门，唤醒肌肉记忆），随后用一根拉杆同时给**门和两台电梯**
供电——玩家要意识到「我拉这一下，整张地图下半场同时活了」，然后两人分头等各自的电梯、
先后登顶，最后在**同一块屋顶、并排的双门**前一起进门。

### 结构（68×24）

```
[出生→箱压板A→门A] → [毒池8格+横移平台] → [总闸拉杆M] → [门M] → [火梯M│屋顶E Q│水梯M]
```

### 关键设计决策

| 决策 | rationale |
|---|---|
| 门 M 与两台电梯共 channel M | 「一对多」是解耦总线唯一能白拿的结构增量：加一台受控物不改任何已有代码 |
| 杠杆放毒池之后、门 M 之前 | 确保玩家先复习「等平台」的节奏，再面对新概念，避免总闸信息过载 |
| 屋顶 6 格高、双门并排、**必须两人都站进门才过关**（Level 判 two-exit 占用） | 单机双门的判定天然要求「两人同时在终点」，不需要任何新逻辑就做出「同台共进」的收尾画面 |
| 两台电梯在门 M 打开后才通电 | 防止玩家提前乘电梯绕过后半程；同时让拉杆有「开闸」的仪式感 |

### edge cases / failure states

- 两人先后登顶：先到者站进自己门内等，`_exits` 只有一 true，不触发过关 → 系统等待，符合预期
- 若拉杆前试图跳上电梯：电梯静止（channel 未激活）→ 无捷径
- 求解器自检确认：不做任何机关时两人均到不了屋顶（无绕过整条链的捷径警告）

## 3. 验证结果（全部通过）

```
python tools/gen_levels.py
  9 个自检夹具全命中 + 8 关静态校验全通过
  （第 7 关输出「通关需要 火娃按住 EB」= 求解器找到的最优解，与设计意图一致）

godot --headless --path . -- --smoke
  levels=8, 每关 240 物理帧无脚本错误
  机关联调：第 7 关 平台2(含受控电梯载客)；第 8 关 平台3(横移+双电梯载客) 问题 0
  finished, errors=0
```

> 工程备注：冒烟看门狗由 90s 放宽到 240s。原因不是死循环——8 关全量在 headless 下
> 按 60fps 节流真实需要 ~95s+，90s 会把「还没跑完」误判成「卡死」。240s 仍能抓住真死循环。

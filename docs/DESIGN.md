# 森林冰火人 —— Godot 4.7 架构设计文档

双人同屏合作解谜平台跳跃游戏原型。零外部美术资源，全部图形程序生成，打开即可玩。

- 引擎：Godot 4.7.2（GL Compatibility，60Hz 物理）
- 状态：可运行原型，4 个关卡，8 类机关
- 运行：Godot 打开 `project.godot` 直接 F5

---

## 0. 设计地基

**Fun Hypothesis（一句话）**

> 乐趣来自**沟通**而不是操作：两个能力互补、物理上分离的角色，必须靠
> 「你去做我做不到的事，我去做你做不到的事」才能推进。

写不出这句话就不该往下做——因为后面每一个机制都要用它过审。

**Design Pillars（3 条，不可妥协）**

| # | 支柱 | 违反它的样子 |
|---|---|---|
| 1 | **一个人永远不够**：每一扇门都必须两个人合力才开得开 | 某个玩家独自跑完全程就通关了 |
| 2 | **元素即身份**：液体既是对方的死亡陷阱，也是自己的专属捷径 | 两人能力对称，换谁来走都一样 |
| 3 | **失误要便宜**：死亡 1 秒重生，不惩罚探索 | 死一次掉进度，玩家不敢试 |

**三条支柱如何落到关卡上**：支柱 1 靠「压力板」实现（人站板上门才开，人一走门就关）；
支柱 2 靠「液体宽度」实现（见 §5 的元素门）；支柱 3 靠死亡只重置位置、不重置机关。

**进阶曲线**

| 关 | 主题 | 新机制 | 认知负荷 | 支柱 |
|---|---|---|---|---|
| 1 | 初识元素 | 元素相克，无机关 | 低：认识「我怕的你不怕」 | 2、3 |
| 2 | 机关重重 | 推箱压板、移动平台、传送门 | 中：单线程因果链 | 3 |
| 3 | 分头行动 | **元素门**（宽液体强制分头）、互相开门 | 高：两条并行路线 + 双向依赖 | 1、2 |
| 4 | 时序接力 | **一次性投资 vs 持续投资**（箱子 vs 人） | 高：分辨资源性质 + 时序 | 1、3 |

第 3 关是曲线上的拐点：前两关是「串联」（你做完我接着做），第 3 关起变成
「并联」（各走各的，谁也替不了谁）。这才是原版灵魂真正开始的地方。

**未验证的部分**（没有 playtest，全是纸面推演）

| 项 | 假设 | 验证路径 |
|---|---|---|
| 单关时长 | 3–6 分钟（首次通关含试错） | 找 2 人试玩计时；若实测 8 分钟以上，第 3、4 关要砍掉一段路线 |
| 第 4 关时序难度 | 玩家能自行分辨「箱子=永久、人=临时」 | 观察是否需要提示；若卡死超过 5 分钟，在关卡开场加一行字幕 |
| 死亡惩罚 | 1 秒重生足够宽容 | 统计单关死亡次数；若中位数 > 15，说明某处地形在骗人 |

## 1. 设计目标与取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 玩法模式 | 本地双人同屏 | 原版灵魂是协作解谜；单人切换会失去「两人互相开门」的核心乐趣 |
| 美术资源 | 全程序化生成（Polygon2D / Sprite2D + 纯色） | 工程零外部依赖、可整体复制；改配色只改 `tex.gd` 一个文件 |
| 关卡格式 | ASCII 网格 + 对象列表 | 地形用字符画最直观；机关带参数用坐标+字典更精确。两者各管擅长的事 |
| 关卡生成 | Python 脚本生成 `.gd` | 手写 50×20 字符画必然数错列；且「能不能跳过去」可以算出来，生成时顺便校验 |
| 输入映射 | 代码里注册，不写 project.godot | 保持工程自包含；改键只改 `input_setup.gd` 一张表 |
| 机关解耦 | channel 信号总线 | 触发器和受控物互不引用，加新机关不改老代码 |

## 3. 场景树

```
Level (Node2D)                     scripts/level.gd
├── CameraRig (Camera2D)           跟随双人包围盒，动态缩放
├── Terrain
│   └── Solid (TileMapLayer)       地形：几百格只有一次绘制调用
├── Hazards
│   └── HazardPool × N             液体池（Area2D），只报「液体种类」
├── Objects
│   ├── PressurePlate / Lever      触发器：广播 channel
│   ├── GateDoor / MovingPlatform  受控物：订阅 channel
│   ├── PushBox                    可推木箱
│   └── Portal × 2                 成对传送门
├── Gems   └── Gem × N
├── Players └── Fire / Water
├── Exits  └── ExitDoor × 2        火门 + 水门
└── HUD (CanvasLayer)
```

**为什么要分 Terrain / Objects 两层：**
地形是无状态的大批量静态格子，交给 `TileMapLayer` 由引擎批量处理；
机关是有状态的独立对象，需要自己的脚本、信号和生命周期。
两者混在一起会导致「几百个机关各自跑 `_process`」的性能陷阱。

## 4. 核心系统

### 4.1 角色控制器（`player.gd`）

火娃水娃共用一份脚本，靠 `element` 与四个输入动作名区分。
加第三个角色不需要改代码，只需在关卡数据里加一个出生点 + 配一组按键。

**手感参数（全部集中在文件头部，改手感只动这里）：**

| 参数 | 值 | 说明 |
|---|---|---|
| SPEED | 240 px/s | 7.5 格/秒 |
| ACCEL_GROUND / ACCEL_AIR | 3600 / 2000 | 地面起步干脆，空中保留惯性 |
| FRICTION | 4200 | 松手急停，实测制动距离 5px（0.16 格） |
| GRAVITY | 1400 | 与 project.godot 默认值一致 |
| JUMP_VELOCITY | -560 | 实测跳跃高度 107px（3.36 格） |
| COYOTE_TIME | 0.10 s | 走出平台边缘后的起跳宽限 |
| JUMP_BUFFER | 0.12 s | 落地前提前按跳的缓冲 |
| JUMP_CUT | 0.45 | 提前松手砍掉上升速度（可变跳跃高度） |

**三个血泪经验：**

1. **Coyote time + 输入缓冲是必需的。** 没有这两个，玩家会觉得「我明明按了跳却没跳」，
   排查半天其实是物理帧和输入帧错位。这两项各 0.1 秒就能让手感天差地别。

2. **液体里的上浮不能加额外阻力。**
   最初写成 `velocity.y = move_toward(velocity.y, FLUID_MAX_FALL, 3000*delta)`，
   本意是「限制下沉速度」，结果它同时也在把上浮速度往下拉——实测一次划水只能升 26px，
   而池子深 32px，**免疫方掉进自己的池子就再也上不来（软锁）**。
   正确写法是只给下沉设上限、上浮交给重力自然减速：
   ```gdscript
   if in_fluid:
       velocity.y = minf(velocity.y, FLUID_MAX_FALL)   # 只限速下沉
   elif velocity.y > MAX_FALL:
       velocity.y = MAX_FALL
   ```
   修完实测上浮 146px（4.57 格）。

3. **死亡补间必须持有句柄并在 `respawn()` 里 kill 掉。**
   死亡动画的补间末尾挂着 `tween_callback(respawn)`。
   如果外部（重生、切关、测试探针）提前调用了 `respawn()`，
   补间仍会在 0.26 秒后再触发一次，把角色强行拽回出生点并清空输入缓冲——
   表现为「刚复活就被瞬移走」。这个问题在冒烟测试里表现为探针测出「跳跃高度 = 0」。

**元素相克：**

| | 岩浆 `^` | 水 `~` | 毒液 `*` |
|---|---|---|---|
| 火娃 | 安全（可游） | **死** | **死** |
| 水娃 | **死** | 安全（可游） | **死** |

判断写在 `Player._is_hostile()`，`HazardPool` 只负责上报液体种类。
加新元素只改角色一个函数，池子完全不用动。

### 4.2 机关系统：channel 解耦

```
触发器 ──emit(channel, active)──> EventBus ──> 受控物
PressurePlate / Lever                GateDoor / MovingPlatform
```

触发器不知道谁在听，受控物不知道谁在触发。
关卡设计师只要保证 channel 名字对得上，连线随便改。

| 机关 | 类型 | 关键参数 |
|---|---|---|
| PressurePlate | Area2D | `channel`。被角色**或木箱**压住时激活；松开即失效 |
| Lever | Area2D | `channel`。站上去按交互键**切换**，自锁保持 |
| GateDoor | StaticBody2D | `channel` + `height`。收到信号后整扇沉入地下 |
| MovingPlatform | AnimatableBody2D | `from`/`to`/`width`/`speed`/`channel`（空 = 一直往返） |
| PushBox | CharacterBody2D | 无。被玩家顶着推，速度 95 |
| Portal | Area2D | `pair`。同 pair 双向连通，两端各 0.55s 冷却 |
| Gem | Area2D | `color`（red/blue）。按颜色归属计分 |
| ExitDoor | Area2D | `element`。只认对应元素，两人都进门才过关 |

**两个实现细节：**

- **移动平台载人**不用引擎的 platform velocity，而是在平台上方放一个薄的乘客检测区，
  每帧把平台自身的位移直接加到乘客 `global_position` 上。
  横向纵向都能用，且不会和角色自己的 `move_and_slide` 打架。

- **推箱子**不用碰撞回调，而是「距离 + 玩家按键方向」直接判断。
  两个 CharacterBody2D 互相挤压时，碰撞回调的触发顺序依赖节点顺序，
  会出现「推不动」的玄学问题；距离判断是确定性的，好调也好查。

### 4.3 关卡数据与生成

**grid 图例：**

| 字符 | 含义 | 字符 | 含义 |
|---|---|---|---|
| `#` | 石头（实体） | `F` / `W` | 火娃 / 水娃出生点 |
| `=` | 木板（实体，视觉区分） | `E` / `Q` | 火门 / 水门 |
| `.` | 空气 | `^` | 岩浆（火娃安全） |
| | | `~` | 水潭（水娃安全） |
| | | `*` | 毒液（都致命） |

**objects 用坐标描述机关**（因为机关需要 channel、高度、行程等参数，ASCII 表达力不够）：

```gdscript
{"type": "door", "cell": [21, 15], "height": 7, "channel": "A"},
{"type": "moving_platform", "from": [22, 20], "to": [33, 20], "width": 3, "speed": 95},
```

**门的方向要特别注意：** `GateDoor` 从 `cell` 所在格**向下**延伸 `height` 格。
所以要封死一条位于第 21 行的通路，门要放在 `(x, 15)` 配 `height: 7`（覆盖 15~21 行）。
只放 `height: 3` 的话门高 96px，而角色跳跃高度 107px——**玩家能直接跳过去**。

### 4.4 双人动态相机（`camera_rig.gd`）

固定缩放无法兼顾「看得清细节」和「两人不出画」。
做法：每帧算包住两人的最小矩形 → 反推缩放 → 夹在 [0.7, 1.4] → 限制在关卡边界内。
平滑用 `1 - exp(-k·dt)` 而不是固定 lerp 系数，保证帧率变化时跟随速度一致。

### 4.5 进度存档

`GameState` 用 `ConfigFile` 存到 `user://progress.cfg`：解锁到第几关 + 每关最好成绩（按用时取优）。
只存元进度，关卡内运行期数据归 `Level` 管——职责边界清晰。

## 5. 运动能力与关卡设计约束（重要）

关卡能不能过，本质是一道几何题。所以先**实测**角色的运动能力，再拿这些数字去约束关卡。
`--smoke` 会打印实测值：

```
[smoke] fire: 跳跃高度=107px(3.36格) 助跑跳远=199px(6.21格) 制动距离=5px(0.16格) 液体上浮=146px(4.57格)
```

| 能力 | 实测极限 | **关卡设计安全值** | 约束了什么 |
|---|---|---|---|
| 跳跃高度 | 107px（3.36 格） | 台阶 ≤ 2 格 | 台阶做 3 格就是帧级操作，玩家会骂人 |
| 水平跳远 | 199px（6.21 格） | 沟壑 ≤ 4 格 | 5 格以上必须给平台/桥 |
| 液体上浮 | 146px（4.57 格） | 池深 ≤ 2 格 | 再深免疫方也游不上来 |
| 制动距离 | 5px（0.16 格） | — | 平台宽度基本不用考虑刹车 |

这些数字写死在 `tools/gen_levels.py` 顶部。**改了 `player.gd` 的手感参数后，必须重跑探针并同步这里。**

### 可达性校验器

`tools/gen_levels.py` 在生成关卡后立刻跑一次 BFS 校验。
它把网格按角色元素转成「可进入 / 不可进入」的格子图
（免疫的液体视为空气、致死的液体视为墙），再按上表的运动能力做扩散，然后检查：

1. **出口可达** —— 走不到自己出口的关卡直接判致命错误、中止生成
2. **宝石可达** —— 按颜色归属（红→火娃、蓝→水娃）检查，只警告
3. **池深不超限** —— 免疫方掉进去游不上来的池子判致命错误
4. 行宽一致、出生点/出口唯一

平台两端与传送门两端会作为额外的连边加入搜索，
所以「必须坐平台过毒池」「只能靠传送门上高台」这类设计也能被正确验证。

### 元素门：用液体宽度当设计语言

这是支柱 2「元素即身份」的实现手段，也是第 3 关之后的核心构图工具。
宽度决定谁过得去：

| 液体宽度 | 免疫方 | 非免疫方 | 用途 |
|---|---|---|---|
| ≤ 4 格 | 涉水通过 | **跳得过去**（≤ 5 格跳远上限） | 通用装饰 / 轻度考验 |
| ≥ 6 格 | 涉水通过 | **过不去** | **元素门**——把两人强制分开 |

校验器必须精确建模这两件事，缺一个就会全盘失真：

- **免疫液体是可站立的**（液面算落脚点）。只把液体当「可跳过的空隙」的话，
  6 格宽的岩浆会变成谁都过不去。
- **致命液体不可站立**。致命液体在物理上是触发区不是实体，踩上去是掉进去死，
  不是站住。只因为它「不可进入」就当地面，角色就能从岩浆顶上走过去，
  元素门彻底失效。（这两个 bug 都是真实踩过的，见 §8 自检。）

### 校验器的能力边界

| 能验证 | 不能验证 |
|---|---|
| 出口/宝石可达性 | **谜题是不是按设计的路解开** |
| 机关链是否可解（含循环依赖） | 跳过一半机关的捷径（只能抓「整条链被绕过」） |
| 一人按板、一人过门的双人协作 | 三人以上的时序、两人同时各按一块板 |
| 木箱能不能被推到压板上 | 操作手感、视觉可读性 |
| 池子会不会软锁 | 谜题好不好玩 |

最后一行左边那条的求解模型：枚举每块压力板的归属（没人 / 火娃 / 水娃），
火娃的可达集按「水娃按住的板」算，水娃反之。它假设两人行动互不阻塞、
且只需一次交接。**它覆盖不了「两人必须同时各按一块板第三扇门才开」。**

### 自检：让校验器证明自己可信

校验器最大的风险不是报错太多，而是**永远通过**——那就等于没有。
`selftest()` 在每次生成关卡前先跑一组夹具，每条都要命中**指定那条规则**
（而不只是「报了点什么」）：

| 夹具 | 必须命中 |
|---|---|
| `gap_too_wide` / `step_too_high` | 出口不可达 |
| `door_circular` / `box_cannot_reach_plate` / `plate_unreachable` | 门解不开 |
| `pool_too_deep` | 池深超标 |
| `gem_unreachable` | 宝石不可达（警告级） |
| `element_gate_blocks` | 元素门生效（非免疫方过不去） |
| `coop_hold_plate` | **判定为可通关**（正例） |

**正例夹具不是可选的。** 只测「坏关卡被抓出来」，一个把所有关卡都判死的
校验器照样能通过反向测试。必须有一组「明明能过、你也得放它过」的关卡。

**这个校验器不是锦上添花。** 第一版两关都是靠它发现致命缺陷的：
第 1 关火焰出口要爬 5 格（跳不上去）、第 2 关酸池 9 格宽（跳不过去，且当时没给平台）。
这类错误在编辑器里肉眼几乎看不出来，玩到那一步才发现。

## 6. 操作说明

| 火娃 | 水娃 | 功能 |
|---|---|---|
| A / D | ← / → | 左右移动 |
| W | ↑ | 跳跃（长按跳更高；在液体里连点 = 划水） |
| S | ↓ | 交互（拉杠杆） |
| R | R | 重玩本关 |
| Esc | Esc | 返回主菜单 |

**宝石归属（硬性规则）**：红宝石只有火娃能拾取，蓝宝石只有水娃能拾取。
异色角色碰到时不会拾取、也不会受伤——宝石压扁弹回、变暗，并提示一句
「红宝石只有火娃拿得到」。归属映射写在 `Gem.owner_of()`，加第三个角色只改这一处。
关卡校验器按同样归属做可达性校验（§5），所以强制归属不会让任何宝石变成拿不到。

## 7. 四关内容

**第 1 关「初识元素」**（46×23）
教学。岩浆池与水潭各 3 格宽、2 格深：火娃可涉岩浆、水娃可涉水潭，
碰上克自己的液体就跳过去（4 格间距，跳远上限 6.21 格，很宽裕）。
池底各藏 2 颗宝石，只有免疫的那个角色拿得到——用奖励而不是堵路来教规则。
终点是三级台阶，每级只高 1 格：水门在第一级，火门在最高一级。

**第 2 关「机关重重」**（52×24）
机关总汇，四段式：
1. 把木箱推上压力板 → 门 A 打开
2. 坐横向移动平台渡 8 格宽的毒液池（远超跳跃极限，必须坐船）
3. 拉下拉杆 → 门 B 打开
4. 涉水潭 / 跳过水潭 → 两级台阶到终点
支线：出生点往左走一格有传送门，通向地面上方 5 格的高台（跳不上去），
台上有 2 颗宝石，拿完跳下来即可。

**传送门位置的设计约束（易踩的坑）：**
传送门入口绝不能放在主干道上。第一版把入口放在压力板与门之间的地面，
结果玩家每次走向门都会被意外传走，白白损失几秒还打断节奏。
正确做法是放在「玩家没有理由经过」的位置——这里选了出生点左侧，
玩家只会往右推进，于是它自然变成需要主动探索的秘密。

**第 3 关「分头行动」**（64×24）—— 曲线拐点，支柱 1+2

上层 / 地面两条路线，靠两道元素门强制分开：
上层 8 格宽岩浆（只有火娃敢过）、地面 8 格宽水潭（只有水娃敢过）。
宽液体就是一道只认身份的门，不需要砌墙。

互相开门的顺序是个死结，只能靠沟通解开：

```
火娃（上层）趟过岩浆 → 拉下拉杆 A ──→ 开水娃路上的门 B
水娃（地面）趟过水潭 → 站住压力板 C ──→ 开火娃路上的门 D（人一走门就关）
火娃趁门 D 开着冲过去 → 拉下自锁拉杆 E ──→ 开水娃路上的门 F
水娃这才敢离开板 C → 走过门 B、门 F → 水门
```

校验器给出的解法正是「水娃按住 C」，与设计意图一致。

**第 4 关「时序接力」**（62×24）—— 支柱 1+3

新机制是让玩家分清两种资源：

| 资源 | 性质 | 代价 |
|---|---|---|
| 压力板 + 木箱 | **一次性投资**，箱子推上去就一直压着 | 前期投入，永久收益 |
| 压力板 + 人 | **持续投资**，人一走门就关 | 一个人被钉住，动弹不得 |

流程：火娃推箱压板开永久门 → 两人坐平台渡毒液池 → 水娃站板 B 钉住自己 →
火娃趟过 6 格岩浆（水娃只能走上面的栈桥绕）→ 火娃拉自锁拉杆 C →
水娃才敢离开板 B 上栈桥 → 各进各的门。

**结构性教训（改了三版才对）：**
最早把水娃设计成「上层全程栈道」，结果火娃顺着栈道走到头直接跳进终点，
整条机关链被绕过。**而且校验器看不出来**——它只验证「能不能到」，
不验证「是不是按设计的路到」。两条全程平行的路线必然给出捷径，
分头必须是「一处 分岔」。所以改成单走廊 + 一段只跨岩浆的绕行栈桥，
两端都用门和地形封死。为此给校验器补了一条兜底规则：
**什么都不做就能到出口 = 存在绕过整条机关链的捷径**（警告级）。

## 8. 测试

```bash
python tools/gen_levels.py                     # 生成关卡 + 校验器自检 + 可达性校验
godot --headless --path . -- --smoke          # 冒烟测试 + 能力探针 + 机关联调
godot --headless --path . -- --smoke --trace  # 额外打印每 20 帧的角色状态
```

四层检查，各自抓不同类型的 bug：

1. **校验器自检**（`selftest()`）—— 每次生成关卡前先跑 9 个夹具，
   8 个必须命中指定规则、1 个必须放行。校验器不可信时直接中止生成。
2. **静态可达性校验** —— BFS 按实测运动能力扩散，验证出口/宝石可达、
   机关链可解、池子不软锁、无绕过整条链死捷径。
3. **关卡冒烟** —— 载入每一关，模拟按键跑 240 物理帧，检查有无脚本运行时错误、
   角色是否生成、出口门数量是否为 2、有无角色死亡/重生异常。
4. **运行时探针** —— 动作能力探针在隔离场景用真实物理帧量出跳跃高度、跳远距离、
   制动距离、液体上浮量；机关联调绕过玩法直接验证平台会动、门会升降、
   压力板→门端到端打通、**杠杆拉下后自锁**（人走开门不关）、传送门已配对。

第 4 层里的机关联调之所以必要：冒烟 AI 通常被第一道门挡住，
后面的平台/压力板一辈子碰不到，等于没被测过。

**局限（诚实清单）：**

- 只验证「机关在物理上能达成」，不验证「谜题是不是按设计的路解开」——
  只能抓出整条链被绕过的捷径，抓不出跳过一半的。这类问题只能靠人工试玩。
- 双人协作求解假设「两人互不阻塞、只需一次交接」，
  覆盖不了「两人必须同时各按一块板」的设计。
- 没有音效、没有手感调优的量化指标（只有能力探针的四个数字）。

## 9. 扩展路线图

按性价比排序：

| 优先级 | 事项 | 说明 |
|---|---|---|
| 高 | 加关卡 | 在 `gen_levels.py` 里加一个 `level_03()`，校验器会自动把关 |
| 高 | 操作级回放验证 | 当前求解器已覆盖箱子推板、机关链和一次交接；下一步补录制回放，覆盖平台时序、真实推箱路径与多次交接 |
| 中 | 美术升级 | `tex.gd` 已集中所有配色；换成真实贴图只需替换这一个文件 |
| 中 | 音效 / BGM | 目前完全无声，残缺感明显 |
| 中 | 更多机关 | 风扇、升降梯、按钮（按下弹起）、定时开关——都只要按 channel 协议实现 |
| 低 | 在线联机 | 需要把 `Level` 改造成权威服务器 + 客户端预测回滚，是另一个量级的工程 |
| 低 | 关卡编辑器 | 数据格式已是纯文本网格，做编辑器主要工作量在 UI |

### 加一个新机关的标准步骤

1. 在 `scripts/objects/` 新建脚本，按现有任意一个机关的 `setup(cell, ...)` 签名实现
2. 触发器类：状态变化时 `EventBus.channel_state_changed.emit(channel, active)`
   受控物类：在 `setup()` 里 `EventBus.channel_state_changed.connect(...)`
3. 在 `level_builder.gd` 的 `match` 里加一个分支
4. 在 `gen_levels.py` 的关卡定义里加对象；若影响通行，在校验器里补对应的连边规则

全程不需要改动任何已有机关的代码——这就是 channel 解耦的收益。
